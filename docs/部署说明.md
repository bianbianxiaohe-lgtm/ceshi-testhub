# TestHub 部署说明

本文档面向**首次在新环境部署 TestHub** 的开发者/运维。按此步骤可在干净的 Linux/Windows 主机上通过 Docker Compose 一键拉起完整系统（MySQL + 后端 + 前端）。

> 事实源：`docker-compose.yml`、`Dockerfile.backend`、`Dockerfile.frontend`、`nginx.conf`、`.env.example`、`requirements.txt`。若 README 与本文件冲突，以本文件 + 实际配置为准。

---

## 一、架构概览

```text
nginx (frontend, :8080)
   ├── /          → 前端静态资源（Vue3 SPA）
   ├── /api/      → 反向代理 → backend:8000
   ├── /admin/    → 反向代理 → backend Django Admin
   ├── /media/    → 反向代理 → 后端上传文件
   └── /static/   → 反向代理 → Django 静态资源
backend (:8000, Django 4.2 + DRF)
   ├── MySQL 8.0（业务库，utf8mb4）
   ├── ChromaDB（嵌入式向量库，持久化到 /app/chroma）
   └── （可选）Redis / Celery worker
```

> **注意**：当前 `docker-compose.yml` 只有 `mysql`、`backend`、`frontend` 三个服务，**未包含 Redis/Celery worker/beat**。需求分析的实时流式输出走 SSE（`StreamingHttpResponse`），不依赖 Celery worker。若启用依赖 `.delay()` 的异步任务，需自行补充 Redis + worker 服务。

## 二、前置条件

| 依赖 | 版本要求 | 说明 |
|------|---------|------|
| Docker | 20.10+ | 含 docker compose 插件 |
| Docker Compose | v2 | `docker compose` 命令 |
| 主机内存 | 4GB+ 建议 | 后端含 ChromaDB + 浏览器引擎 |
| 主机磁盘 | 10GB+ | 镜像 + 数据卷 |

可选：
- **AI 模型服务**：OpenAI-compatible 接口（Chat + Embeddings）。无可用模型时，流程仍能跑，但 AI 分析类功能会失败。
- **真机/浏览器自动化**：墨刀读取需 Chromium（Dockerfile 已装）；App 自动化需 adb + 手机。

## 三、环境变量配置

仓库只提交 `.env.example`（无真实密钥）。**首次部署必须复制并填写真实值**：

```bash
cp .env.example .env
vi .env
```

必须修改的关键项：

```ini
# 数据库（mysql 容器初始化和 Django 连接共用）
MYSQL_ROOT_PASSWORD=请改成强密码
MYSQL_PASSWORD=请改成强密码
DB_PASSWORD=请改成强密码          # 与 MYSQL_PASSWORD 保持一致
DB_HOST=mysql                      # 容器内用服务名，不要改成 127.0.0.1

# Django
SECRET_KEY=生成一个随机长字符串     # python -c "import secrets; print(secrets.token_urlsafe(50))"
DEBUG=False
ALLOWED_HOSTS=localhost,127.0.0.1,你的服务器IP或域名

# 访问入口（前端 nginx 代理地址）
CORS_ALLOWED_ORIGINS=http://你的IP或域名:8080
CSRF_TRUSTED_ORIGINS=http://你的IP或域名:8080

# 邮件（用于驳回邮件/通知，可选）
EMAIL_HOST_USER=
EMAIL_HOST_PASSWORD=
```

> ⚠️ **绝不要把真实 `.env` 提交到 git**。`.env` 已被 `.gitignore` 忽略。

## 四、构建与启动

```bash
# 1. 拉取代码（main 分支为最新稳定）
git clone <你的仓库地址> testhub
cd testhub
git checkout main

# 2. 配置环境变量
cp .env.example .env
# 编辑 .env（见上）

# 3. 构建并启动（首次会较慢，需下载镜像 + 依赖 + Playwright Chromium）
docker compose up -d --build

# 4. 查看状态
docker compose ps
docker compose logs -f backend   # 观察 docker_start.py 自愈初始化
```

**启动流程**（backend 容器）：
`CMD ["python", "docker_start.py"]` — 该脚本会：
1. 等待 MySQL 就绪
2. 幂等地做数据库初始化（`DELETE django_migrations` → 幂等加列 → `migrate --fake`）
3. 启动 Django `runserver 0.0.0.0:8000`

> 后端经 Django `runserver` 提供（非 Gunicorn），适合内网/中小规模。若需高并发，可自行改为 Gunicorn + 前置反代。

## 六、首次使用需在界面配置

代码不含业务初始数据，首次使用需在**系统配置 / 配置中心**（前端页面）录入：

1. **AI 模型配置（必须）**：录入 OpenAI-compatible 的 Chat 与 Embeddings 模型账号（URL、Key、模型名），并设 `is_active=true`。
   - 需求分析会用 `role='writer_vision'`（视觉/OCR）、`role='embedder'`（向量）等角色配置。
   - 建议各角色各配一个可用模型，且 Embedding 角色需 `is_active=true`（向量去重依赖）。
2. **用户/项目/版本**：创建用户、项目后，需求分析模块才能关联功能模块。
3. （可选）**知识库**：墨刀需求分析会向 `kb_{project_id}` Chroma 集合写向量，无需手动建库。

## 七、升级与热更新

**重新部署新版本：**
```bash
# 拉最新代码
git pull
# 重建并重启（docker-compose.yml 变化时需重建）
docker compose up -d --build
# 若镜像名未变，容器不会自动重建，需强制：
docker compose up -d --build --force-recreate
```

**容器内文件热更新（紧急修复，不重新构建镜像）：**
```bash
# 后端
docker cp ./apps/xxx.py testhub-backend:/app/apps/xxx.py
docker restart testhub-backend   # 触发 docker_start.py 自愈初始化

# 前端（nginx 静态目录）
docker cp dist/. testhub-frontend:/usr/share/nginx/html/
docker exec testhub-frontend rm -rf /usr/share/nginx/html/assets/   # 先清旧 hash
docker exec testhub-frontend nginx -s reload
```

> ⚠️ 热更新在容器 recreate 后会丢失（回到镜像内旧内容），正式发布请用 `docker compose build`。

## 八、常见问题（FAQ）

**Q1: backend 容器一直重启循环？**
- 检查 `.env` 的 `DB_HOST` 是否为 `mysql`（不是 127.0.0.1）
- 检查 MySQL 是否 healthy：`docker compose ps`
- 看日志：`docker compose logs backend | tail -50`

**Q2: 前端构建很慢 / 网络问题？**
- Dockerfile 使用清华 pip 镜像，若网络受限可自行替换 `Dockerfile.backend` 中的 `-i https://pypi.tuna.tsinghua.edu.cn/simple`
- npm 安装可设 `npm config set registry https://registry.npmmirror.com`

**Q3: 墨刀读取失败 / 需要登录？**
- 原型需登录时，在阶段0 粘贴 Cookie（`form.cookies`）
- 读取依赖 Playwright Chromium，若浏览器引擎未装成功，日志会提示

**Q4: 没有 AI 模型能用吗？**
- 纯读取/导航可跑，但结构化、澄清、测试点、用例、PCI 等 AI 环节会失败
- 必须先配置可用模型

**Q5: 数据库迁移冲突？**
- `docker_start.py` 已做 `migrate --fake` + 幂等加列自愈，一般无需手动干预
- 若手工改过库结构，需确认目标库状态后再跑迁移，避免重复执行
