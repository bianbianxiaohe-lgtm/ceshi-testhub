# 墨刀需求分析流程与模型调用说明

> 用途：一份可直接查阅的墨刀（Modao）需求分析全链路说明，覆盖各阶段「做什么 / 调哪个模型角色 / 关键机制」。
> 最后核对：2026-07-28（开发库 `testhub_dev`、生产库 `testhub` 均已逐项查证）
> 代码入口：`apps/requirement_analysis/modao_workflow.py`（编排）、`modao_extractor.py`（阶段0读取）、`views.py` / `modao_views.py`（接口与配置组装）

---

## 0. 整体流程总览

```
用户贴墨刀链接
      │
      ▼
[阶段0] 原型读取（Playwright 逐页 + 双路融合 + OCR）        ← analyzer + writer_vision + writer_vision_ocr
      │   产出 extracted_json（含 fused_requirements）
      ▼
[阶段1] 需求结构化（YAML 摘要：模块清单 + 需求概述）          ← analyzer
      ▼
[阶段2] 需求澄清（识别模糊/缺失/边界 → 澄清清单）             ← analyzer
      ▼
[阶段3-1] 用例设计第一段：模块拆分→测试点→风险→PCI→三路合并（向量去重）  ← analyzer + embedder
      ▼
[阶段3-2] 用例设计第二段：测试用例生成→冒烟→质量自检→Excel   ← writer（用例）+ analyzer（冒烟/质量）
      ▼
[阶段4] 冒烟执行决策（前端驱动，后端记录 passed/rejected）    ← 无模型调用
```

**人工确认闸门**：最终测试用例 / 冒烟 / 质量报告 / Excel 的导出，必须经过「服务端人工批准」（不以单纯前端确认弹窗为准）。批准记录绑定当前 `clarification_log` 与 `final_testpoints_json` 的 SHA-256 指纹；批准后修改任一内容，旧批准自动失效，必须重新确认。C/D 级证据内容必须由人工填写结论，模型建议不能直接当正式需求。

## 1. 阶段0：原型读取

- **触发**：用户提供墨刀在线链接、发起分析时自动触发。
  - 单地址：自动枚举页面树，发现目录内多页。
  - 多地址：每个地址当单页抓（避免页面树枚举导致跨地址重复）。
  - webshare：始终枚举页面树。
- **执行过程**（`ModaoExtractor`，Playwright 驱动）：
  1. 浏览器打开链接（`networkidle` 60s / `domcontentloaded` 30s）。
  2. 识别侧边栏可点击页面行：选择器 `.rn-list-item.page[data-cid][data-interactive-target-type="6"]`（注意：内部 `.screen-item-icon` 图标点击不可靠，必须点页面行）。
  3. 逐页点击，切换后 `wait_for_timeout(2000)`（即等待 2 秒）再提取。
  4. 提取内容：可见 UI 文字（`_extract_visible_text`）+ 批注/编号注释（`_extract_annotations`，选择器含 `[class*="note"]` / `[class*="annotation"]` / `.note-item`）+ 整页截图（jpeg）。
  5. **双路融合（默认开启）**：每页同时保留 `dom_text`（DOM 文字）与 `vision_text`（截图视觉理解），用 `analyzer` 跨两路交叉融合为 `fused_requirements`。
  6. **截图 OCR 补充**：对每页截图批量调用 `writer_vision_ocr` 提取画布内视觉需求（并发，`OCR_CONCURRENCY=5`），合并进需求。
- **产物**：`extracted_json`，含每页 `{dom_text, vision_text, annotations, screenshot, screenshot_sha256, visual_summary, ...}` 与顶层 `fused_requirements`、`warnings`。
- **质量门禁（任一触发即标记 `failed` 并阻断后续）**：
  1. 没有读取到任何页面；
  2. 多页时重复截图比例 > 20%（画布切换不可信）；
  3. 双路融合下视觉识别失败率 > 20%；
  4. 双路融合结果为空，或 > 20% 的页缺少 `source_pages` 来源证据。
- **调用模型**：
  | 用途 | 角色 | 开发库 | 生产库 |
  |---|---|---|---|
  | 双路文本×视觉融合 | `analyzer` | id=9 deepseek-chat | id=10 deepseek-chat |
  | 截图视觉理解 | `writer_vision` | id=3 qwen-vl-max | id=3 qwen-vl-max（3条active取首条） |
  | 截图 OCR 补充 | `writer_vision_ocr` | id=7 qwen-vl-plus | id=9 qwen-vl-plus |

## 2. 阶段1：需求结构化

- **输入**：阶段0 的 `fused_requirements`（双路融合需求）。
- **做什么**：用 `p0_requirement_struct` 提示词生成 **YAML 结构化摘要**——含业务**模块清单（`modules`）**与需求概述（`requirement_summary`）。
- **重要性**：阶段1 锁定的 `modules` 清单是阶段3-1 模块拆分的**硬约束来源**（治本修复：曾因 LLM 在长文本中漏模块，已改为把清单注入拆分 prompt，强制 name 对齐、不得省略）。
- **调用模型**：`analyzer`（开发 id=9 / 生产 id=10）。

---

## 3. 阶段2：需求澄清

- **做什么**：复用 `p0` 能力，识别需求中的**模糊 / 缺失 / 边界**问题，生成**澄清清单**。
- **证据等级**：结构化结果用 A/B/C/D 等级。C（模型建议/需求缺失）、D（证据验证失败）级内容必须由**人工填写结论**，不能把模型建议直接当正式需求。
- **调用模型**：`analyzer`（开发 id=9 / 生产 id=10）。

---

## 4. 阶段3-1：用例设计第一段（测试点合并）

- **输入**：阶段1 结构化摘要 + 阶段2 澄清结论。
- **步骤（均走 `analyzer`）**：
  1. **模块拆分**（`p1_module_split`）：以阶段1 `modules` 清单为硬约束，输出各模块测试点骨架（YAML）。遗漏模块时带遗漏清单**自动重试一次**，仍遗漏才 `failed`。
  2. **测试点生成**（`p2`）：逐模块展开测试点。
  3. **风险识别**（`p5`）：识别质量风险点。
  4. **PCI 生成**（`p6`）：生成隐私/合规/安全相关子问题（PCI）。
  5. **三路合并 + 向量去重**：把「测试点 / 风险 / PCI」三路合并去重。
- **向量去重（embedder，方案A）**：
  - 取 `embedder` 配置对测试点描述做向量化，按 `dedup_threshold` 余弦相似度去重。
  - 去重必须写 `dedup_audit_json`（保留项 / 删除项 / 相似度 / 阈值 / 原因），不只记删除数量。
  - `embedder` 缺失时降级为「无去重」。
- **调用模型**：
  | 用途 | 角色 | 开发库 | 生产库 |
  |---|---|---|---|
  | 拆分/测试点/风险/PCI/合并 | `analyzer` | id=9 deepseek-chat | id=10 deepseek-chat |
  | 向量去重 | `embedder` | id=8 qwen text-embedding-v3 | id=8 qwen text-embedding-v3 |

---

## 5. 阶段3-2：用例设计第二段（用例生成）

- **前置**：基于已人工确认/批准的测试点。
- **步骤**：
  1. **测试用例正文生成**：用 `writer` 角色生成最终测试用例（`case_prompt`，max_tokens=16000）。**这是整个流程里唯一使用 `writer` 的步骤**。
  2. **冒烟用例生成**：`analyzer` 生成冒烟用例（`smoke_prompt`）。
  3. **质量自检**：`analyzer` 生成质量报告；`overall_result=FAIL` 或存在 `blocking_issues` 时状态标记失败、不得导出正式 Excel。
  4. **Excel 导出**：复用 `module_exporter` 样式；**须经服务端人工批准**后才导出正式文件。
  5. PCI / 风险回复、质量报告等辅助生成也走 `analyzer`。
- **调用模型**：
  | 用途 | 角色 | 开发库 | 生产库 |
  |---|---|---|---|
  | **测试用例正文** | `writer` | id=2 deepseek-chat | id=2 deepseek-chat |
  | 冒烟用例 / 质量自检 / PCI·风险回复 | `analyzer` | id=9 deepseek-chat | id=10 deepseek-chat |

---

## 6. 阶段4：冒烟执行决策

- **驱动方**：前端（用户决策），后端只记录 `passed` / `rejected`。
- **模型调用**：无（不涉及 LLM）。

## 8. 配置取用逻辑（改模型时看这里）

- **`analyzer`**：`resolve_configs` 优先 `get_active_config('siliconflow','analyzer')`，取不到再 `filter(role='analyzer', is_active=True).first()`。两环境 analyzer 都是 deepseek（非 siliconflow），走兜底取到。
- **`writer`**：`filter(role='writer', is_active=True).first()`。
- **`embedder`**：`get_active_embedder()` = `filter(role='embedder', is_active=True).first()`（**按 role 取，不是 model_type**）。两环境 id=8 均存在 → 向量去重真实生效。
- **`writer_vision` / `writer_vision_ocr`**：在视图层 `modao_views.py` 单独查询（不在 `resolve_configs` 内）：
  - `writer_vision` = `filter(role='writer_vision', is_active=True).first()`
  - `writer_vision_ocr` = `filter(role='writer_vision_ocr', is_active=True).first() or writer_vision`（未单独配则回退 writer_vision）
- **回退**：`resolve_configs` 中若 `analyzer` 缺失而 `writer` 存在，则 `analyzer = writer`（文本 LLM 可共用）。两环境 analyzer 均已存在，不触发回退。
- **生效方式**：配置从 DB 实时读取，**改 `AIModelConfig` 无需重启后端**，下次跑分析即生效。
- **角色清单**（`ROLE_CHOICES`）：`writer` / `writer_vision` / `reviewer` / `analyzer` / `browser_use_text` / `writer_vision_ocr` / `embedder`。

## 9. 已知约定与坑

- 阶段0 逐页读取必须用**截图 SHA-256** 校验独立画布；重复截图 > 20% 直接阻断。
- 阶段3-1 模块拆分必须**覆盖阶段1 模块清单**，遗漏自动重试一次，仍漏则失败。
- 质量报告 FAIL / 有 blocking_issues → 保留产物但标记失败且**不得导出正式 Excel**。
- 双路融合禁止对全部页面做固定长度整体截断；按完整页面分批，单页极端超长才分片。
- 人工确认前允许完成读取/分析/澄清/测试点合并，但**不得生成最终测试用例、冒烟、质量报告或 Excel**。
- `reviewer` 用于测试评审模块，不参与墨刀生成链路（上表列出仅供对照）。
