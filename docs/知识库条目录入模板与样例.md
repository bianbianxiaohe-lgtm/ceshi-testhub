# 项目知识库录入模板与样例

> 用途：人工新增 / 修改项目知识库条目时，按本文规范填写，可让 AI 在生成测试用例时**精准按需求语义召回**，避免同名不同义功能（如新旧版本「引导」）被错误命中。
>
> **澄清一个常见误解**：AI 生成用例时**本来就能根据具体需求文本判断「这几个引导是不是同一个功能」**（它读得懂需求里写的是「快手渠道引导」还是「首页引导」）。所以下面这些约定**不是给 AI 的判断力兜底**，而是给**召回阶段**用的——AI 提炼时虽然能判断，但前提是「正确的知识条目」得先通过 RAG 的 top-K（默认 8 条）召回进它的视野。同名功能一多，真正相关的那条会被挤出 8 条名额，AI 看不到自然就判断不了。**因此核心是让 content 写具体（含业务区分词），前缀只是辅助保险。**

---

## 一、先选对录入路径

| 路径 | 注入方式 | 适合放什么 |
| --- | --- | --- |
| **DB 知识条目**（ProjectKnowledge，走 RAG 语义检索） | 按需求文本语义检索 top-K（默认 8 条） | 需要**按需求精确定位召回**的细粒度知识：具体功能约束、术语定义、某版本特有规则 |
| **文件系统 `.md` 知识库**（全量注入） | 每次生成**整体**拼进 prompt | 项目级总体背景：产品概述、整体架构、通用约定（不放细粒度功能，否则又变全量灌入） |

> 结论：**绝大多数人工录入应走 DB 条目**；`.md` 只放全局背景。本文重点给 DB 条目的模板。

---

## 二、DB 知识条目模板（走 RAG，优先用）

### 字段说明

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `title` | ≤200 字，**建议带【功能/版本】前缀**（辅助 RAG 区分，真正的区分来自 content 具体化） | 召回时的标题信号，同名功能靠它+bcontent 强化区分 |
| `category` | 5 选 1（见下） | 只影响分组展示，不影响检索 |
| `content` | 自由文本，**开头点明适用范围 + 写得具体（含业务区分词）** | 实际喂给模型的内容；**区分度的根本来源** |
| `is_active` | 默认 true | false 会自动从向量库删除，不再被召回 |
| `sort_order` | 默认 0 | 仅同组内排序，不影响语义召回 |

`category` 五选一：
- `background` 业务背景
- `terminology` 关键术语
- `test_focus` 测试重点
- `constraints` 约束条件
- `notes` 注意事项

### 召回增强建议（不是铁律，是让 top-K 更稳的保险）

> 前提：AI 生成时已能结合需求判断功能异同。**下面这些是给召回阶段加区分信号，避免同名条目过多时正确条目被挤出 top-K。**

1. **同名功能尽量写版本/业务域**（如 `【引导 / v1.6.1】` vs `【引导 / v1.0.1】`）：只写「引导功能」时两条相似度都高，会同时挤占 top-K 名额。
2. **content 要写具体业务场景**（含"快手渠道""首页右上角""H5 落地页"等区分词）——这是**区分度的根本**，比前缀更重要。前缀只是给写得不够具体的条目兜底。
3. **一条只讲一个功能 / 一个约束**，粒度别太粗（否则召回噪声大）。
4. **不写废话**：「本功能很重要」「需要充分测试」这类泛化句会污染 top-K，挤掉真正相关的具体内容。

### 推荐 content 结构

```
【功能名 + 版本/业务域】一句话定义
约束：xxx
测试重点：xxx
```

## 三、DB 条目样例（直接照抄改内容）

### 例 1：约束条件（constraints）—— 带版本前缀，区分同名功能

```
title:     【引导 / v1.6.1】新增快手渠道的引导优化
category:  constraints
content:   【引导 / v1.6.1】本版本引导新增快手渠道入口，与旧版 v1.0.1 的五步注册引导不同。
          约束：快手渠道必须走 H5 落地页，不能直接调起 App；授权回调域名限定为 kuaishou.example.com。
          测试重点：验证未安装快手 App 时引导降级为 H5；验证回调域名错误时给出明确提示。
```

```
title:     【引导 / v1.0.1】老版注册引导五步流程
category:  constraints
content:   【引导 / v1.0.1】旧版注册引导为固定五步，含短信验证码环节。
          约束：短信验证码 60 秒内不可重发；连续失败 5 次锁定 10 分钟。
          测试重点：验证验证码过期、重发冷却、锁定解锁时效。
```

### 例 2：关键术语（terminology）

```
title:    【订单 / 全局】"已锁单"状态定义
category: terminology
content:  【订单 / 全局】"已锁单"指用户提交但风控挂起的状态，既非待支付也非已支付。
         约束：已锁单不可直接取消，必须由风控审核通过后流转；超时 30 分钟自动转为"已取消"。
         测试重点：验证锁单期间支付入口置灰；验证超时自动取消并释放库存。
```

### 例 3：测试重点（test_focus）

```
title:    【支付 / 跨境】跨境支付金额精度要求
category: test_focus
content:  【支付 / 跨境】跨境支付涉及多币种换算，金额精度为小数点后 4 位（非 2 位）。
         测试重点：验证日元→美元换算保留 4 位；验证展示金额四舍五入但结算以 4 位为准；
         验证汇率失败时的降级提示而非报错中断。
```

### 例 4：注意事项（notes）—— 来自历史风险处置

```
title:    【登录 / 全局】弱网下的登录重试风暴
category: notes
content:  【登录 / 全局】历史故障：弱网环境登录按钮未做防抖，导致重复请求触发账号临时锁定。
         处置：前端登录按钮点击后 3 秒内禁用；后端对同设备 1 分钟内的登录请求做幂等去重。
         测试重点：弱网（限速 50kbps）下连续点击登录，验证只发 1 次请求且不会误锁。
```

### 例 5：业务背景（background）—— 适合项目级通用约定

```
title:    【账户体系 / 全局】账号打通规则
category: background
content:  【账户体系 / 全局】App 账号与 Web 账号已打通，使用同一手机号为主键。
         约束：一个手机号仅可绑定一个实名主体；换绑需原手机号短信验证 + 人工审核。
         测试重点：验证换绑全流程；验证已实名账号不可重复实名。
```

## 四、文件系统 `.md` 知识库模板（全量注入，只放全局背景）

放在项目知识库目录下的 `.md` 文件，每次生成整体拼入 prompt。**不要放细粒度功能约束**（那应走 DB 条目）。

```markdown
# 产品概述
XXX 是一款面向 C 端的电商 App，核心链路为：浏览 → 加购 → 下单 → 支付 → 履约。

# 整体架构约定
- 前端统一走网关 `api.example.com`，禁止直连后端服务。
- 所有写操作必须带幂等键 `Idempotency-Key`。

# 通用测试原则
- 资金相关链路必须覆盖幂等与对账。
- 涉及个人信息的接口必须走脱敏。
```

## 五、常见错误（务必避免）

| 错误 | 后果 |
| --- | --- |
| 两条「引导」都只写 `引导功能` 且 content 也泛泛 | 语义接近，top-K 同时召回且挤占名额，AI 反而看不到真正相关的那条 |
| content 写具体业务场景（含区分词） | 即使不加前缀，向量也能自然区分，召回更准 |
| 一条 content 堆 5 个不相关功能 | 召回噪声大，精准度下降 |
| content 全是「需要重点测试」之类泛化句 | 污染 top-K，挤掉真正相关内容 |
| 改 DB 不通过 API / 界面，直接 UPDATE | Chroma 向量不更新，检索到旧内容或已删内容 |
| 中途更换 embedding 模型 | 向量空间不一致，必须重建该项目 Chroma 集合 |
| 细粒度功能约束塞进 `.md` | 又变全量灌入，失去 RAG 意义 |

> 注：通过知识库管理界面 / API 的新增、修改、禁用、删除都会**自动同步 Chroma 向量**；墨刀流程阶段 3 确认后系统也会自动沉淀带版本前缀的条目，无需手工重复录入同类内容。
