# 禅道覆盖分析与 AI 闭环 · 实现说明

> 本文档说明「AI 用例 ↔ 禅道 Bug 覆盖率分析」与「缺陷反馈 → 知识库 → 生成进化」闭环的
> 实现方式、当前进度与剩余步骤。更新日期：2026-08-17。

## 一、总体架构

```
禅道(18.6) ──同步──▶ TestHub zentao_bugs ──▶ 覆盖率分析 ──▶ 覆盖率报告
                                                      │
                                                      ▼
                                            未覆盖缺陷 + 调优建议
                                                      │
                                          自动归因 + 适用范围分类
                                                      │
                                                  ▼
                                        项目知识库(RAG/版本化)
                                                      │
                                                  注入生成提示词
                                                      │
                                                  ▼
                                       下一次 AI 用例生成(自动规避已知缺陷)
```

- 后端应用：`apps/zentao`（同步、分析、知识库写入、报告 API）
- 前端页面：`frontend/src/views/zentao/ZentaoCoverage.vue`（菜单：智能用例生成 → 禅道覆盖分析）
- 数据表：`zentao_configs` / `zentao_bugs` / `zentao_sync_logs` / `zentao_coverage_reports` / `zentao_coverage_items` / `zentao_product_mappings`

## 二、已实现模块

### 1. 禅道同步

- **登录**：禅道网页会话（`refreshRandom` + `md5(md5(密码)+随机串)`），失败自动换全新会话重试 3 次；请求失败会重置会话并恢复执行上下文后重试。
- **数据获取**：按「产品 → 执行」拉取 Bug，`m=execution&f=bug` 精确获取当前执行（单页 20 条）。
- **分页兜底**：执行接口无法翻页时，回退到产品浏览分页 + 按执行号过滤 + 收集够目标数提前停止；已处理该禅道版本“`executionID` 必须在 `browseType` 之前，否则返回空”的参数顺序坑。
- **幂等入库**：按 `(config, zentao_id)` upsert；禅道删除的 Bug 标 `is_active=False`；拉取为空时跳过失效标记，避免误删。
- **产品/执行下拉**：支持未保存配置时用临时账号探测（`probe_products` / `probe_executions`）；产品映射（TestHub 项目 ↔ 禅道产品名，如 轻卡日常 ↔ 卡鲁狸）自动匹配。

### 2. 覆盖率分析（embedding + LLM）

- **双通道粗召回**：① 通义 `text-embedding-v3` 语义向量，余弦相似度取 Top15（候选间相似度 ≥0.95 的去重）；② 纯 Python BM25 关键词检索（CJK 2-gram）取 Top15。
- **RRF 融合**：两路排序按 `1/(k+rank)` 倒数加权合并（k=60），取 Top15 送精排。
- **本地精排**：本地部署 `bge-reranker-base`（放在宿主机 D 盘，不占 Docker 盘），对 Top15 重排取 Top5；服务不可用时自动降级为 RRF 排序。
- **阈值截断**：精排最高分 < 0.7 直接判定“未覆盖”并跳过 LLM（`auto_uncover_rerank`），节省 token；仅在精排可用时生效。
- **关键词兜底召回**：候选里没有与 Bug 共享专属词（3 字中文片段，如“还原按钮”）的用例时，强制补入最多 2 条，解决“正确用例排在候选外”的漏召回。
- **置信度分级**：相似度 ≥0.90 自动判定覆盖、≤0.40 自动判定未覆盖，中间模糊区间才调 LLM（v4-pro）。
- **批量判定**：模糊区间每批 6 个 Bug 一次 LLM 调用，输入用精简文本（标题+预期结果，截断），输出 JSON 数组。
- **假断言复核**：对“已覆盖”条目再批量复核一次，断言笼统或路径无关的判为假覆盖并剔除（`fake_covered_count`）。
- **补漏建议**：未覆盖 Bug 汇总后由 LLM 按功能点生成可落地的补测建议 + 知识库沉淀建议。

### 3. 知识库闭环（缺陷反馈 → RAG）

- 「将未覆盖缺陷+调优建议写入知识库」按钮：把每条未覆盖 Bug 写成 `[缺陷模式]` 条目 + 1 条 `[覆盖缺口调优建议]` 汇总。
- **自动归因**：LLM 判定每条缺陷是 `AI需求误解 / 代码缺陷 / 用例设计/覆盖缺失`。
- **适用范围分类**：LLM 判定 `仅本版本 / 全局通用 / 老功能优化（跨版本参考）`；版本性条目绑定版本，其余跨版本生效。
- **版本化 RAG**：知识条目带 `version` 标记并写入 Chroma 向量（metadata 带 version_id）；生成用例时只注入「全局知识 + 当前版本知识」，无关版本不会参考（已验证：版本 19 注入、版本 999 不注入）。
- **幂等**：重复写入按标题更新，不产生重复条目。

### 4. 来源标识与指标体系

- `testcases.source`：`ai`（AI生成）/ `manual`（人工编写）/ `unknown`（未标记）。**两条生成线的采纳入库都自动标 `ai`**（AI用例生成线 3 个入口 + 墨刀需求用例线 3 个入口），手工新建默认 `manual`；列表/表单可查看修改；提供 `mark_case_source` 批量标记命令。
- **真实覆盖率** = 库内 AI 用例数 ÷ 该版本用例总数 ×100%（即 AI 用例占比，提案口径的简化）。
- **采纳率** = 库内该版本 AI 用例数 ÷ 该版本 AI 生成任务产出的用例总数 ×100%（产出数由 `final_test_cases` 的 `TCxxx` 统计；无生成任务记录时显示“数据不足”）。
- **需求使用率** = 用例覆盖的功能模块数 ÷ 该版本全部功能模块数 ×100%。
- **覆盖率目标**：每个配置可设目标（默认 90%），报告显示达标/未达标。
- **Bug 级覆盖率** = 判定覆盖的 Bug 数 ÷ 该版本 Bug 总数 ×100%（主报告指标）。

### 5. 前端页面

- 配置管理（项目/版本/产品/执行自动匹配、记住账号密码、覆盖率目标）
- 同步 Bug（同步完成前“覆盖率”按钮置灰，前后端双重校验）
- 覆盖率报告列表 + 明细抽屉（逐条覆盖/未覆盖、匹配用例、相似度、判定理由、补漏建议、指标）
- 一键写入知识库

## 三、指标口径与数据来源

| 指标 | 公式 | 数据来源 | 说明 |
|---|---|---|---|
| Bug 级覆盖率 | 覆盖 Bug 数 / 版本 Bug 总数 | zentao_bugs + 判定结果 | 主指标 |
| 真实覆盖率(AI占比) | AI 用例数 / 用例总数 | testcases.source | 需先标记来源 |
| 采纳率 | AI 用例数 / 生成任务产出用例数 | testcases.source + testcase_generation_task.final_test_cases | 无任务记录时数据不足 |
| 需求使用率 | 用例覆盖模块数 / 版本模块数 | feature_modules + testcases.feature_modules | 按模块口径 |
| 假覆盖剔除数 | 复核判定不精确的已覆盖条目 | 二次 LLM 复核 | 防“假覆盖” |

## 五、剩余步骤

### P1（建议下一步）

1. **异常场景类型统计注入**：把未覆盖缺陷的共性场景类型（边界值/并发/网络中断/权限不足/状态回显）统计出来，动态追加到生成 Prompt 的“异常场景强制覆盖”段落。
2. **对话式分步拓展**：生成结果页支持“帮我拓展测试点X的边界值”“合并测试点XX”等指令，逐步深挖隐性规则。
3. **人工复核入口**：报告里对“假覆盖剔除”和“LLM 判定”提供人工修正，修正结果回写并影响后续知识库。

### P2（需要更多基础设施）

4. **CI/CD 增量生成**：接入代码仓库（GitLab/Jenkins）变更事件，对新增/变更区域自动补用例。
5. **覆盖率健康度看板**：多版本趋势、低于阈值自动触发优化器。
6. **模型/提示词库版本化迭代**：每个 Sprint 评估一次生成质量并调整提示词库。

## 六、已知口径与注意事项

- LLM 判定存在一定随机性，同一批 Bug 两次跑覆盖率可能略有波动（已用低温度、批量结构化输出降低波动）。
- 历史用例（轻练 109 条 / 卡鲁狸 222 条）来源为“未标记”，真实覆盖率/采纳率需先标记（`mark_case_source --version-id X --source ai`）才有意义。
- 采纳率依赖该版本存在“已完成”的生成任务且 `final_test_cases` 可统计；早期版本可能显示“数据不足”。
- 界面优化类 Bug（`bug_type=interfaceoptimize`）不参与覆盖率计算（分母与判定均排除），报告单独列出条数（`ui_optimization_bug_count`）并在前端展示。
- 禅道 REST `/api.php/v1` 在本服务器未放行，当前用会话 JSON 接口实现；如需标准 REST token，需在禅道 nginx 增加 PATH_INFO 转发。

## 七、部署说明

- 生产容器：`testhub-backend`（Django）与 `testhub-frontend`（nginx 静态页）。
- 后端改动需 `docker cp` 到容器后 `docker restart testhub-backend`；前端需 `npm run build` 后拷贝 `frontend/dist` 并重启 `testhub-frontend`。
- 数据库直建表/加列脚本：`_create_zentao_tables.py`（因仓库迁移图历史问题，schema 变更走手工 SQL）。
- 本地 reranker 服务：venv 与模型在 `D:\testhub-reranker\`（服务端口 8002，模型不占 Docker 盘）。已配置开机自启（Windows 启动文件夹 `TestHub_Reranker.bat`，登录自动运行）。启动脚本源码在 `scripts/start_reranker.bat` / `scripts/reranker_server.py`，计划任务模板在 `scripts/reranker_task.xml`（需管理员注册）。服务停止时覆盖率分析自动降级为 embedding 召回，不影响主流程。
