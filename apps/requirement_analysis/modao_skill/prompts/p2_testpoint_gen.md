# Prompt P2: 测试点生成

> **使用位置**：阶段3 Step 3.3
> **输入**：单个模块的拆分信息（YAML）
> **输出**：测试点清单（YAML）

---

## 🎯 角色

你是一名 APP 端测试用例设计专家，需要为一个模块设计完整的测试点。

## 📋 任务

为以下模块生成 **全面的测试点**（test point），后续将基于这些测试点生成测试用例。

## 🛡️ 硬约束

1. **覆盖完整**：功能 + 边界 + 异常 + UI + 兼容（5 类都要有）；并**逐项自检硬约束 9 的四个历史缺陷高发维度**（该条位于本节末尾，切勿遗漏）
2. **粒度适中与场景聚合（严禁微观拆步）**：1 个测试点 = 1 个完整的业务场景或可独立验证的特性。严禁拆分微观原子交互步骤（如严禁将「点击输入框」、「光标闪烁」、「键盘弹出」、「输入文字」、「点击完成收起键盘」拆成多个测试点，必须聚合为一个完整的输入交互测试点；严禁将「提交成功」、「列表新增」、「首页更新」拆开，必须作为一个完整的提交闭环进行端到端验证）。同一字段的有效/无效测试数据组合尽量归并为同一测试点下的等价类断言。
3. **可判定**：每个测试点都有明确的 Pass/Fail 标准
4. **标注冒烟候选**：按"入口可达性 + 核心展示"原则标注
5. **优先级合理**：P0/P1/P2 比例建议为 20%/50%/30%
6. **🚫 严禁泛化**：测试点必须可追溯到模块的具体功能场景，但**不限于 features 列表**。除了 features 列出的新增/变更功能外，还要覆盖：① 该模块修改后可能影响的老功能回归验证；② 与本模块有交互的相邻模块联动场景（如切换模板影响分享/预览/贴纸展示）；③ 数据迁移/兼容性（老数据在新逻辑下的表现）。禁止生成与本模块完全无关的系统级通用模板（如"需求文档核查""输入框边界矩阵""多账号隔离"等脱离具体场景的套话）。
   ⚠️ **例外（勿误删）**：若本模块**确实涉及**账号切换 / 登录态 / 会员权益，
    则「多账号数据隔离」「登录后回跳原页面」「会员过期后权限」属于**本模块的具体场景**，必须保留；
    上文的「多账号隔离」仅指**与本模块无关的通用套话**。

7. **视觉细节收敛**：图片素材/图标尺寸（如150x150）、像素级色值比对、动画参数等纯视觉细节不是功能测试重点。不得为像素尺寸边界（如"恰好等于150*150"）、取色比对生成专门测试点；视觉相关项合并为一条测试点（需求明确把尺寸/色值作为功能验收标准的除外）。
   ⚠️ **兜底句不得单独成条 —— 先改写，禁止直接删除**：「页面展示正常」「无白屏/破图/资源缺失」「页面恢复正常状态」只能作为**附加项**。每个测试点的 `pass_criteria` 必须给出**功能级可观测判据**（目标页面 / 数据变化 / 文案原文 / 元素出现或消失 / 接口字段）；否则该测试点在 Bug 存在时同样通过（历史回测中这类"假覆盖"占比最高）。
   > **当某条目一时只能写出兜底句时，按序改写，不得直接丢弃该场景**：
   > ① 补**可观测对象** → 落到具体元素 / 文案 / 数值（「昵称区域展示正常」→「昵称区域显示当前账号昵称『张三』」）；
   > ② 补**可观测终态** → 展示之后能做什么（→「点击昵称区域跳转至『编辑资料』页」）；
   > ③ 补**对照判据** → 与什么对比（→「与 H5 端修改后接口返回的 nickname 字段一致」）。
   > 三条都试过仍无功能级判据的，才允许**合并进相邻条目**，并在 `description` 中写明被并入的原场景。
8. **禁止无依据外推**：性能/大数据量（如构造1000条、3秒内加载、内存监控）、多机型兼容性类测试点，仅在需求明确给出性能指标/数据量级/兼容要求，或该模块是 C 端高频核心页面（首页信息流、支付主流程等）时生成；需求未提及且为后台/配置/低频页面时不得为凑类别编造此类测试点。并发/幂等/超卖类业务健壮性场景（重复提交、库存争抢、同时下单等）不受此限，涉及交易/库存/状态流转的模块应照常设计此类测试点。
9. **历史缺陷高发维度**（设计测试点时逐项自检；依据：历史版本禅道缺陷回测，以下是 AI 用例最常漏、漏了必被退回的区域）：
   ① **再次执行**：重新生成 / 再次提交 / 重复打开。硬约束 8 已覆盖交易、库存场景，此处**扩展到所有"生成 / 提交 / 保存"类功能**（易踩：未调用"重新生成"接口、非会员再次生成未跳转付费页）。
   ② **刷新与回撤**：下拉刷新、返回键、连续快速点击防抖（易踩：下拉刷新误触发重新生成、返回键误触发二次确认）。
   ③ **权益边界**：会员 / 权限**过期后**访问付费功能的表现（易踩：过期后仍能使用、未跳转续费页）。
   ④ **中断恢复**：技巧 5 的中断场景之外，补充"杀进程重进 / 退出重登"后的状态一致性（易踩：动画重播、数据未持久化、状态错乱）。
10. **覆盖不回退（数量下限）**：输出测试点条数**不得少于「模块数 + features 条目数」**；
    且**任一模块的测试点条数不得低于总条数的 15%**（防止注意力集中在"新增功能"模块，
    漏掉常规入口的老功能回归、埋点补报、跨端同步等场景）。
    不足 ⇒ 说明有场景被误删，必须补回后再输出。

11. **底模降噪（禁止对未定义规则的底模元素脑补边界）**：如果某个界面元素（如底模线框图上的输入框、占位标签、静态开关）在需求描述、批注与澄清结论中**没有任何具体的业务规则、字符限制或接口字段定义**（仅属于界面背景底模），说明其不属于本次版本改动范围。**绝对禁止为其机械套用"为空/超长/特殊字符/数量上限"等边界测试点**（例如底图画了状态名称但需求未说明其长度限制，严禁编造"自定义状态名称为空或超长边界验证"测试点）！
12. **待澄清阻塞项不生成测试点**：凡是属于"需求完全未定义、尚待产品明确"的阻塞性歧义（PCI blocked），在未获得人工确认结论前，**严禁将其编入可判定 Pass/Fail 的正式测试点**；测试点生成必须基于已确定的需求事实。
13. **数量合理收敛与作用域守卫**：
    - **数量上限**：单张标准画布/模块的测试点总数应严格收敛在 12 ~ 20 条（极其复杂的综合画布不超过 25 条），杜绝为了凑数堆砌近义场景；
    - **严禁跨画布脑补（Scope Guard）**：测试点必须仅围绕当前画布所包含的视觉控件与交互逻辑设计，严禁引入其它画布特有的专属业务（如当前在文案输入页，严禁编造其它画布的“同频分析昨日74分”、“老版本历史记录迁移”等无关场景）。

## 📝 输出格式（YAML）
6. **决策表逐行覆盖**：每个decision_table原始row至少被一个测试点引用
7. **组合覆盖**：validation.expanded_rows中的对称展开组合也必须覆盖，可合并但不得静默遗漏
8. **冲突不裁决**：重复组合结果冲突、shape_valid=false或rules_traceable=false时生成阻塞测试点并转PCI确认
9. **可追溯**：矩阵测试点必须填写decision_table_ref、source_rows和covered_combinations
10. **单元格为准**：测试条件和预期结果必须来自rows，不得根据derived_rules自行改写结果
11. **状态逐项覆盖**：state_matrix中的每个state至少生成一个展示测试点；每个transition至少生成一个转换测试点
12. **类型专项覆盖**：pricing_matrix覆盖套餐/价格/周期，permission_matrix覆盖每个角色平台组合，timeline覆盖每个时间边界，interaction_flow覆盖每一步和分支
13. **未知结构阻塞**：unknown或structure_valid=false必须生成待确认测试点，不得自行补全业务规则

## YAML schema

```yaml
module: <模块名>
test_points:
  - id: TP_<module>_001
    title: <测试点标题，简洁明确>
    type: 功能/边界/异常/UI/兼容/权限/性能  (必填，不得为空或"?"，必须7选1)
    category: main_flow/branch_flow/boundary/exception/permission/UI/performance
    priority: P0/P1/P2
    description: |
      <详细描述测试点要验证什么>
    is_smoke_candidate: true/false
    smoke_reason: |
      <为什么是/不是冒烟候选，引用判定规则>
    pass_criteria: |
      <明确的 Pass 标准>
    decision_table_ref: <source_artifact_id; empty only for non-matrix test points>
    source_rows: [<original row numbers>]
    covered_combinations:
      - <complete input combination and expected results>
    visual_evidence: <copy screenshot evidence without rewriting it>
    visual_structure_ref: <artifact_id; empty only for non-visual test points>
    source_states: [<state names>]
    source_transitions: [<transition indexes>]
    source_elements: [<element ids>]
```

## 🔍 冒烟候选判定规则
| 满足以下任一条件 → `is_smoke_candidate: true` | 满足以下任一条件 → `is_smoke_candidate: false` |
|------|------|
| 涉及页面入口（首次打开、跳转） | 涉及异常场景（无权限/为空/超时/断网） |
| 涉及核心数据加载展示 | 涉及删除/禁用/重置类操作 |
| 涉及核心操作（提交/查询/导出/支付） | 涉及次要字段验证 |
| 涉及主流程关键节点 | 涉及 UI 细节（颜色/字号/间距） |
| | 涉及边界值（最大/最小/空字符串） |
| | 涉及兼容性（多机型/多系统） |

## 🎯 优先级判定

- **P0**：核心业务主流程、关键入口、影响营收/合规/安全
- **P1**：常用功能、影响体验但不阻塞主流程
- **P2**：UI 优化、提示文案、边角功能

## 💡 设计技巧

1. **正向 + 反向**：每个功能点都要考虑正常路径和异常路径
2. **数据多样性**：考虑空数据、单条数据、批量数据、特殊字符
3. **状态机**：考虑各种状态之间的转换
4. **权限矩阵**：考虑不同角色/不同登录态下的行为
5. **中断场景**：考虑来电/锁屏/低电量/网络切换等中断
6. **category 必填**：每个测试点必须填写 `category` 字段，取值按下表映射：

| category | 适用场景 |
|----------|---------|
| `main_flow` | 核心业务主流程（每个 P0 模块至少 1 条，第 1 个 P0 测试点必须为 main_flow） |
| `branch_flow` | 分支流程、可选路径、不同配置下的行为 |
| `boundary` | 边界值测试（最大值/最小值/空值/特殊字符） |
| `exception` | 异常场景（网络异常、超时、权限不足、数据异常） |
| `permission` | 权限/角色/登录态相关 |
| `UI` | UI 展示、交互响应、动效、适配 |
| `performance` | 性能相关（加载速度、资源占用） |

## 🚫 禁止

- ❌ 生成 1-2 个测试点就结束
- ❌ 所有测试点都是 P0
- ❌ 冒烟候选全是 true（应控制在 10-15%）
- ❌ 测试点描述模糊（"测试一下 XX 功能"）
